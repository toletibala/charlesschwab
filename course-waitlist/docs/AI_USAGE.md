## 1. Prompts used

Each prompt gave the model a role, the relevant code, hard constraints, and a fixed output format. The "Principle" column names the technique.

### P1: Concurrency tests

> You are a senior Python engineer reviewing a small enrollment service.
>
> **Context:** `RegistrationService` (below) guards `enroll` and `drop` with one `threading.Lock`. Capacity and duplicate checks happen before writes, so without the lock two threads could both take the last seat. [`service.py` and the `make_service` test helper pasted here]
>
> **Task:** write unit tests that start threads at the same moment and show the lock keeps state correct. Cover exactly three scenarios: (a) 20 learners racing for 3 seats, (b) one learner sending 10 enroll requests at once, (c) 8 concurrent drops of the same enrolled learner while two others wait.
>
> **Constraints:** standard library only (`unittest`, `threading`). Do not use `sleep` to create the race; use a `threading.Barrier`. Each test builds a fresh service. Do not change `service.py`. After each scenario assert `check_invariants() == []`.
>
> **Output:** one `unittest.TestCase` class, no explanation. Then, in 3 bullets, say how I can prove these tests fail when the lock is removed.



### P2: Prerequisite and skip-policy edge cases

> You are a QA engineer reviewing a FIFO waitlist.
>
> **Policy (mine):** a learner must have PASSED the prerequisite. It is checked at enroll time and again when they reach the front of the waitlist. If a learner at the front is ineligible, they are SKIPPED, removed from the queue permanently, and promotion continues. Only learners at the front are evaluated.
>
> **Task:** list the edge cases most likely to break this policy in `_promote_from_waitlist` [function pasted here]. For each give: the setup, the expected result, and the one-line reason it could fail.
>
> **Constraints:** at most 8 cases, ordered by risk. Do not propose changing the policy, and do not propose new features such as leaving the waitlist or notifications. Mark any case that is a policy question rather than a bug.
>
> **Output:** a table with columns `#`, `setup`, `expected`, `risk`, `policy question?`.
